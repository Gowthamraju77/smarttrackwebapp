### B1 — Queue and identity implementation missing at review time

**Affected dependency:** K9 queue/wire headers and source, plus K8 `firmware/src/main.cpp` callers. Queue/wire filenames are not specified by the contract; the review searched all available firmware sources rather than assuming a filename.

**Consequence:** there is no executable path to determine whether a short write is reported as success, an incomplete tail hides subsequent unsent records, record IDs survive reboot/retry, or an acknowledgement/compaction checkpoint can destroy unsent data.

**Required next step:** land those implementations, then trace append, recovery, identity allocation, enqueue-result handling, retry, exact receipt matching, queue cursor persistence, and any compaction. Replace/extend the availability gate with implementation-specific isolated fault-injection tests. Source availability by itself does not resolve this review.

| # | Fault or transition | Required observable outcome |
|---|---|---|
| 1 | Append one record successfully; restart the queue | Exact payload and original record ID replay once as pending. |
| 2 | Short write at every framing/header boundary | No false durable-success result; all previously durable unsent records remain readable. |
| 3 | Power loss at every payload/trailer byte boundary | Complete records remain recoverable; incomplete/corrupt tail is not transmitted as a valid record. |
| 4 | Reopen a torn-tail queue, append another record, then restart | Recovery does not make the new complete record or an earlier unsent record unreachable behind the damaged tail. |
| 5 | Full card, zero-byte write, open failure, and failed durable commit where observable | Enqueue failure is propagated to callers; existing unsent data is not truncated or overwritten. |
| 6 | Restart after successful persistence but before first transmission | Retry uses the stored record ID and exact payload, without allocating a replacement identity. |
| 7 | Server accepts a record; response is lost; restart and retry | Same record ID is sent again; duplicate-accept receipt can retire it without losing another record. |
| 8 | Restart around boot/sequence/ID allocation persistence; include telemetry and SOS | Newly created records cannot accidentally reuse an existing device/record identity; recovered pending records keep their original identity. |

| 10 | Power loss during acknowledgement checkpoint and compaction/rotation, if implemented | Pending unsent records survive every mutation boundary; recovery may replay an accepted record but must not silently skip an unsent one. |
