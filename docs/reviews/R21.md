## Contract and pending review checks

The contract specifies unique `(device_id, record_id)` identities, exact UTF-8 payload CRC validation, durable transactional ingest, and `{accepted:true,record_id,duplicate:boolean}` as the only queue-removal receipt. Because such a receipt permits removal of the submitted queue record, a same-ID/different-payload submission must not silently receive success for a different stored record. The exact error status and payload comparison mechanism still need to be inspected in the implementation.

These ten distinct checks remain blocked; they are a review plan, not ten executed or passed checks:

1. Telemetry identity is enforced by a database uniqueness constraint on `(device_id, record_id)`, not solely an application lookup.
2. SOS identity has corresponding durable uniqueness; the intended telemetry/SOS ID namespace is explicit.
3. An identical telemetry retry retains one stored record and returns the original ID with `accepted:true, duplicate:true`.
4. An identical SOS retry retains one event and does not duplicate related durable effects.
5. The same telemetry ID with a different payload is rejected without changing the original record or acknowledging the conflicting submission.
6. The same SOS ID with a different payload likewise cannot receive a queue-removal receipt for the wrong event.
7. Distinct devices may use the same record ID without colliding; another device's record cannot produce this device's duplicate receipt.
8. Concurrent same-ID submissions use transaction/uniqueness handling that cannot falsely accept a losing different-payload submission. Static inspection alone cannot prove live concurrent behavior.
9. Record insertion and associated durable effects share appropriate transaction boundaries; failure cannot produce a success receipt or leave partial committed effects.
10. HTTP handlers preserve the database result's ID and duplicate status, fail closed on RPC errors/malformed results, and emit success only after the durable operation succeeds.
