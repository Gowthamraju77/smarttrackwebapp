## Findings and integration requirements

### 1. Blocking dependency: no sensor or calibration implementation is available

- **Evidence:** firmware inventory has only `firmware/include/ui/` headers; the isolated prerequisite test fails because `firmware/src/main.cpp` is absent. Searching the firmware headers for calibration, MPU, TinyGPS, NMEA, HardwareSerial, and Wire acquisition paths returned no matches.
- **Consequence:** no evidence that values originate from hardware, that failed I2C/UART reads invalidate previous values, or that calibration failure prevents a valid-looking motion sample. UI readiness flags alone do not demonstrate sensor success.
- **Next step:** review K8's acquisition and calibration implementation and its callers once present, then follow the sample through K9's wire serialization. Sensor failure and missing values must be visible through that complete path.

### 2. Missing-value representation needs an explicit integration contract

**Static interface observation; a production regression is not established because the acquisition-to-UI adapter is absent.**

- `firmware/include/ui/types.h:8` defaults `gpsFix` and `imuReady` to false, which correctly keeps an entirely uninitialized device from claiming sensor readiness.
- `firmware/include/ui/types.h:10-11` also defaults coordinates, speed, HDOP, acceleration, gyro, and fix age to numeric zero. The state has no individual speed/age/acceleration/gyro availability flags and no explicit calibration status.
- `firmware/include/ui/page_gps.h:16-21` accepts a fix age of zero as fresh and a speed of zero as valid. Therefore a caller that sets a genuine position fix and coordinates but leaves absent speed/age at their defaults produces a displayed `0.0` m/s and `0.0s`, rather than unavailable values. This is a conditional caller/representation hazard, not proof that an existing adapter currently does so.
- The GPS page correctly rejects non-finite/out-of-range coordinates, hides fixes older than five seconds, hides non-finite/negative speed, and hides non-positive HDOP. The default false fix flag also hides all numeric defaults. These are static observations, not executed C++ tests.
- **Required integration decision:** carry per-field availability from the parser/sensor to serialization and display. Initialize unavailable floating values with an explicit non-finite sentinel or add validity bits; use an explicit invalid age/age-valid indicator; expose failed/pending calibration separately from sensor initialization. Serialize absence as JSON `null`, never a manufactured zero. Preserve genuinely measured zero speed, zero gyro, and valid zero latitude/longitude; rejecting every zero would also be wrong.
