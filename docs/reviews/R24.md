## Required executable coverage after implementation

1. An authorized acknowledgment performs its own state change and records authenticated actor, tenant, event identity, prior/new state, and server time in durable audit evidence.
2. Resolution is a separate supported action; its legal starting states and required evidence are enforced by the authoritative persistence layer.
3. Repeated requests and concurrent acknowledgment/resolution cannot move a resolved event backwards or overwrite the original transition evidence. Retry responses and audit cardinality follow the implemented idempotency contract.
4. State and transition audit commit atomically; an audit-write failure cannot leave an unaudited state change. Audit history cannot be rewritten through permitted client roles.
5. Every role (`owner`, `admin`, `responder`, `viewer`), unauthenticated requests, and cross-tenant users exercise both transitions. The contract names these roles but does not fully specify the allowed transition matrix; confirm the intended matrix before treating role behavior as correct. Do not infer that naming a role grants mutation privileges.
6. Rejected/invalid transitions leave state and successful-transition evidence unchanged; any rejection audit is clearly distinguished from a completed transition.
7. Protected HTTP handlers and direct database/RPC access enforce consistent role and tenant limits; invalid IDs/actions, missing configuration, and origin failures cannot bypass those limits.
